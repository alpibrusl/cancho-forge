# Many repositories, no per-merge approval, one human gate: the demo

> **Status: design, nothing built, nothing measured.** Every claim about what Forge will do is *(designed)*. Every claim about what
> Forge does now is taken from [`company.md`](company.md) on `main` at `2cf52ff` and was **not** checked against the code. If this
> document and the code disagree, the code is right and this document is corrected in place.

## 1. The problem, in two sentences

Today a person is asked before every merge, every pin bump and every release, and Forge works on one project at a time (the
operator's `gates.<id>` names one repo per qa step). A company over the cancho language and its `cancho-*` repositories needs the
person to look at **one thing: a demonstration, generated by Forge, that the work is done and works**, and at nothing else.

Goal: a person approves a demo; everything that led to it (branches, pull requests, pin bumps, merges) happened without asking, under
rules the person wrote once.

Non-goals: Forge choosing what to build (see [`intents.md`](intents.md)), Forge editing its own rules, anything that needs a person to
trust a model's word.

## 2. The principle: merge authority comes from evidence, not from a person

A merge asks one question: *is the evidence that this change is good complete?* Where a program can answer it, a person adds nothing but
delay. The existing rule already says so: a worker's `done` is a claim, acceptance is Forge running the check itself against an artifact
it hashed (`company.md` section 8). This design extends the same rule one step: **Forge may merge a pull request when a written policy
holds, and the policy is the operator's, not the worker's and not the manifest's.**

What a person still decides, once, in advance: the policy, the registry, the oracles, the budget, and the demo. What a person no longer
decides: any individual merge inside that.

## 3. The repository registry *(designed)*

Today `gates` in the operator file names, per step, a repo, a revision and a checkout. Add a **registry**: a closed JSON file, the
operator's (outside the company directory, like the operator file), listing every repository the company may touch.

```json
{
  "repos": {
    "cancho":       { "slug": "alpibrusl/cancho",       "branch": "main", "gate": "scripts/gate.sh",
                      "pins": [],                          "needs": [],            "owner": "builder",
                      "policy": "compiler" },
    "cancho-code":  { "slug": "alpibrusl/cancho-code",  "branch": "main", "gate": "scripts/test-all.sh",
                      "pins": [".cancho-rev"],             "needs": ["cancho"],     "owner": "builder",
                      "policy": "default" },
    "cancho-forge": { "slug": "alpibrusl/cancho-forge", "branch": "main", "gate": "scripts/gate.sh",
                      "pins": [".cancho-rev", "cancho.toml"], "needs": ["cancho", "cancho-code"], "owner": "builder",
                      "policy": "default" }
  },
  "policies": {
    "default": {
      "require": ["gate", "authority-ceiling", "audit", "review"],
      "protected": ["policy/**", "registry.json", ".github/**", "eval/**/oracle*", "eval/audit_*"],
      "max_files": 40, "max_added_lines": 1500
    },
    "compiler": { "require": ["gate", "authority-ceiling", "audit", "review", "selfhost"], "protected": ["..."],
                  "max_files": 80, "max_added_lines": 4000 }
  }
}
```

* `needs` is the dependency order of the repositories (a compiler change reaches the tools that pin it; a tool does not reach the
  compiler). `pins` are the files that name another repository's revision.
* `gate` is a command the registry names; the manifest still cannot name a repo, a checkout or a command (`company.md` section 3).
* The `gate` of each repository already exists; the registry only records it. The allow-list of the gate runner becomes the registry's
  key set, in one place (today it is a list in the runner and a second in `docs/self-hosting.md`).

Refusal tags *(designed)*: `registry-malformed`, `registry-unknown-field`, `repo-unknown`, `repo-cycle`, `policy-unknown`.

## 4. The merge policy *(designed)*

A pull request is **mergeable by policy** when every item in its policy's `require` list has a record from a program Forge ran, against
the pull request's head commit:

| item | what it is | who produces it |
|---|---|---|
| `gate` | the repository's gate command, green, on a throw-away checkout of the head commit | the qa step (`repo.gate`), exists |
| `authority-ceiling` | `cancho authority` of every program, compared to the checked-in ceiling; a widening needs the ceiling file changed **in the same pull request**, and that file is protected (below), so a widening is never mergeable by policy | reviewer step; **today the reviewer is qa under another name** (`company.md` section 11); this is the first thing to build |
| `audit` | the held-out audit for the package the change touches, at or above the score recorded for its base commit | analyst step over an oracle the builders never saw (section 6) |
| `review` | a verdict from a reviewer that did not build the change and did not see the builder's context | a separate model step, own context, given the diff and the brief only |
| `selfhost` | for the compiler only: the compiler rebuilds and the pinned dependents' gates stay green | qa steps of the repositories that `need` it |

And these must also hold, whatever `require` says:

* **Nothing protected is touched.** `protected` paths are the policy itself, the registry, CI configuration, the oracles and audits,
  release workflows and credentials. A pull request that touches one is **never** mergeable by policy: it waits for a person, and the
  person is asked about that change only, in words ("this changes what may be merged"), not about merges in general. This closes the
  loop in which a builder weakens the rules that judge it.
* **Size.** More than `max_files` or `max_added_lines` is held. A large change is split or seen.
* **Budget.** The company's budget is not exhausted (`company.md` section 9).
* **No failed or unavailable check.** A check that cannot judge holds the pull request, as a held step does today.
* **Same head.** All records are for the head commit the merge would land. A new push voids them.

Refusal tags *(designed)*: `merge-evidence-missing` (with the item), `merge-protected-path`, `merge-too-large`, `merge-head-moved`,
`merge-budget`, `merge-check-unavailable`.

### How the merge happens, without giving Forge the keys

Forge does not hold a token that can merge anywhere. It holds a **GitHub App** (or a fine-grained token) limited to the registry's
repositories with exactly: open pull requests, push to branches named `forge/*`, write commit statuses, enable auto-merge. Not admin,
not workflow dispatch, not `main`.

Each repository's branch protection requires one status, `forge/evidence`, which only Forge writes, and only when section 4's list
holds for the head commit. Forge enables auto-merge; **GitHub merges when the status appears**. So the rule that no one may push to
`main` stays enforced by the host, not by Forge's good behaviour, and a bug in Forge cannot widen what it may merge beyond "things its
own policy accepted". *(This needs branch protection and the App installed on each repository. Neither was checked for any
`cancho-*` repository; it is the operator's one-time setup.)*

## 5. Cross-repository work: the pin task *(designed)*

The manual work of this project's last weeks, made a task type `pin.bump` (role builder, no model step):

1. Input: a target revision of repository R (for example the compiler at `f4ead824`).
2. Forge computes the **affected set** from the registry: every repository that lists a `pin` and has R in its `needs`, transitively,
   in `needs` order.
3. For each, in order: branch `forge/pin-<R>-<rev8>`, write the pin files, run the repository's `gate` on the result, open the pull
   request, collect the evidence of section 4, and let it merge by policy. The next repository starts only when the previous one is
   **merged**, because its gate may read the previous one's `main`.
4. A repository whose gate is red stays an open pull request with its report; the rest of the set that does not depend on it goes on.
5. The task's result is a **table**: repository, pull request, evidence, state (`merged`, `red`, `held`). The set is *complete* only when
   every row is `merged`. It is never reported done otherwise, and the demo (section 6) shows the table.

This is the case that cost most by hand: a pin merged into a stale base branch left a repository on the old compiler with every check
green. The fix is a step 3 rule: after each merge Forge reads the pin from the **target branch** and compares it to the target revision;
a mismatch is `pin-not-landed`, not done.

Refusal tags *(designed)*: `pin-target-unknown`, `pin-not-landed`, `pin-set-incomplete`.

## 6. The one human gate: the demo *(designed)*

The existing `human_gates` stay, but a company meant to run unattended has **one**: `demo`. Everything before it is automatic.

A **demo** is a directory Forge builds, from a clean checkout of the merged heads, by running a script from the company directory and
recording what it did:

| part | content | produced by |
|---|---|---|
| `claims.md` | what the work was for, copied from the brief and the intent as written by a person; Forge adds nothing | the product step's own text |
| `run/` | the **brief's worked examples** executed against the built artifact, with command, input, output, exit code, in order | a replayable script, run by Forge, not by the builder |
| `audit.json` | the score of the held-out audit, by group, next to the score the builder's own checker gave | the analyst step |
| `change.md` | repositories, pull requests, commit ids, the pin table, the authority diff (empty is stated as empty) | Forge from its journal |
| `cost.json` | tokens and dollars by step, from `usage.jsonl` | Forge |
| `hashes` | a hash of every file above | Forge |
| `replay.sh` | one command that redoes `run/` on a clean machine and compares the output to the hashes | Forge |

The person reads `claims.md`, looks at `run/`, checks that `audit.json` is a pass, and runs `replay.sh` if they doubt it. Then
`forge company decide <dir> demo approved <reason>`.

Two changes to `decide` *(designed)* that make the gate mean something:

* A `demo` decision records **the hash of the demo directory**. A decision on any other hash, or one recorded before the demo exists,
  does not count (this is the "pre-approved gates" gap, `company.md` section 14, closed for this gate).
* An `approved` demo is what authorises the **release** (publishing, section 7), and only for the commit ids in that demo.

**What the demo proves, said plainly.** It proves the artifact does what the examples in the brief say, that a held-out audit the
builders never saw agrees, and that the change set landed as described. It does not prove the brief was the right brief (that is the
Intent, [`intents.md`](intents.md)), and it can be gamed by a builder that sees the audit. So: the oracle and the audit are protected
paths, live outside the builder's execution directory, and their results are shown **beside** the builder's own, because the studies
of this project (cancho-code #83) found a build that reported `done` and scored 0 of 54 on the audit.

Refusal tags *(designed)*: `demo-incomplete` (a part missing), `demo-hash-mismatch`, `demo-before-evidence`.

## 7. What stays with people, always

* The registry, the policies, the oracles and audits, the budget: changes to them are pull requests that touch protected paths, so
  policy never merges them.
* **Releases.** Publishing a release (`release.yml` with `publish=true`, a tag, a package) needs the credential Forge does not hold.
  After an approved demo, the person (or a second, narrower credential held for that one workflow) triggers it for the commit ids of the
  demo. One decision, one release.
* Raising the limits of section 4.
* Turning the whole thing off: `forge company decide <dir> demo rejected` stops the merges queued behind that demo; nothing already
  merged is reverted (section 8).

## 8. What can go wrong, and what we do about it

| risk | consequence | mitigation in this design |
|---|---|---|
| builder weakens a check or an oracle | a bad change merges | those are protected paths; never merged by policy |
| a reviewer rubber-stamps | evidence says `review` but means nothing | separate context; the reviewer's verdict is one item of several, never the only one; measure its agreement with the audit before trusting it |
| the audit is too narrow | green and wrong | the demo shows it beside the builder's score; an audit per package is written first, by a person |
| a merged change is bad and the demo is rejected | `main` has it | merges are plain commits: revert is a normal pull request, itself under policy; the rejection records which commits |
| Forge's token is stolen | open PRs and branch pushes, nothing on `main` or releases | the App's scope in section 4 |
| the policy is wrong for a repository | too much or too little is auto-merged | start every repository at `default` with `max_files` small, widen with measured evidence |
| cost runs away | budget | `merge-budget`; merges stop, the demo is built from what landed |

## 9. What this document does not decide

1. Whether `main` of each repository is protected today and whether an App can be installed (an operator fact).
2. Whether `review` is a model or a program for the first slice. The recommendation is to ship without it and require it only after its
   verdicts are compared with the audit on past pull requests (the project has plenty).
3. Whether the demo includes a recording. `docs/demo/forge-demo.mp4` exists; a recording is nice for a person and is not evidence.
4. The format of `replay.sh` beyond "one command".

## 10. Build order

Each step ends with a gate that reaches its refusal tags and, where it spends money, a measured run recorded in `spike/RESULTS.md`.

1. **Registry** and its check verb (`forge registry check`); the gate runner reads its allow-list from it. No behaviour change.
2. **Reviewer distinct from qa**: the authority-versus-ceiling comparison (the missing half of `company.md` section 11).
3. **Policy evaluator** as a pure function over records, with every tag of section 4 tested; no GitHub yet. This is where the policy is
   argued, on recorded pull requests from this project.
4. **`pin.bump`**, run against the real repositories in dry-run (branch and gate, no merge), then with the status and auto-merge.
5. **Demo builder** and the `decide` hash binding.
6. A measured end-to-end run on one small package, with a person approving only the demo, recorded with its cost.

Steps 1 to 3 touch no network. Nothing here is a claim until step 6 is run.
